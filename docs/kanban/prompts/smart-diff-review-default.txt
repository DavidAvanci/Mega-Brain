# Revisão guiada a partir do smart-diff

O smart-diff já faz a parte determinística: recolhe formatação (por arquivo e por trecho), lockfiles e arquivos gerados; resolve imports (tsconfig `paths`, `import()`, pacotes, convenção de nome de teste); ordena por dependência (`readingOrder`); e lista fatos por símbolo (`symbols`). O agente faz as decisões que não podem ser determinísticas. O script de revisão incluído no Mega Brain valida e monta o resultado.

Você decide três coisas, sempre em um arquivo `decisions.json`:

1. **Ruído por julgamento**: arquivos que o smart-diff deixou visíveis mas não precisam de atenção.
2. **Seções**: agrupar os arquivos restantes em fluxos com título e resumo, sem quebrar a ordem de dependência.
3. **Explicações**: para cada arquivo das seções, como era e como ficou.

Nunca edite o JSON final à mão: mude `decisions.json` e rode `assemble` de novo.

## 1. Obter o relatório do smart-diff

- Local do smart-diff: `$SMART_DIFF_DIR`, senão `~/smart-diff`. Se `dist/packages/cli/src/index.js` não existir, rode `yarn install && yarn build` nessa pasta. Se o repositório não existir, pare e peça o caminho ao usuário.
- Pasta de trabalho: o scratchpad da sessão quando houver; senão, um `mktemp -d`. Chame de `<work>`.
- Rode o CLI **de dentro do repositório analisado**, com o modo de comparação que o usuário pediu:

```bash
node "$SMART_DIFF_DIR/packages/cli/bin/smart-diff.cjs" --range BASE...HEAD --format json > <work>/report.json
```

  Outras formas: `--base main` (merge-base com HEAD), `--staged`, sem flag (working tree), ou `--pr https://github.com/OWNER/REPO/pull/N` (qualquer diretório; repo privado precisa de `GITHUB_TOKEN`/`GH_TOKEN`). Sem indicação do usuário, use `--base` com o branch padrão (`master`, ou `main` se não existir).
- Se o usuário entregou um `report.json` pronto, use-o. Se ele não tiver `readingOrder` e `groups[].relations`, foi gerado por uma versão antiga: gere de novo com o comando acima.

## 2. Preparar a lista de trabalho

```bash
node "<script-de-revisao>" prepare <work>/report.json <work> --cache <cache>
```

`<cache>`: o caminho que o usuário indicar; senão `<work>/cache.json`. Se existir um cache de uma rodada anterior do mesmo diff, passe-o: é assim que reexecuções saem iguais.

O script escreve `<work>/worklist.json` e um patch por arquivo em `<work>/patches/` (já sem os trechos que o smart-diff marcou como formatação). Para cada arquivo visível, `worklist.json` traz:

- `order`: posição na ordem de leitura do smart-diff;
- `path`, `status` (`A` novo, `M` modificado, `D` removido, `R…` renomeado), `kind` (`code`, `test`, `doc`, `config`);
- `classifications`: por exemplo `behavior_candidate` (a sintaxe mudou) ou `partial_format` (parte dos trechos era só formatação);
- `lines`: linhas adicionadas e removidas;
- `formatHunksOmitted`: quantos trechos de formatação foram tirados do patch;
- `dependsOn` e `usedBy`: arquivos alterados que ele importa e que o importam;
- `relations`: a evidência de cada dependência;
- `symbols`: declarações adicionadas, removidas ou modificadas, com assinatura antiga e nova;
- `patchFile`: o patch filtrado;
- `cached`: a decisão anterior, quando o conteúdo do arquivo não mudou desde a última rodada.

`autoNoise` lista o que o smart-diff já recolheu. Não repita esses arquivos em `noise`. Só coloque um deles numa seção se o patch mostrar algo que precisa de revisão, como um lockfile com um upgrade que o manifesto não explica. Nesse caso, ele passa a exigir explicação.

**Leia todos os patches antes de decidir.** Para diffs grandes (mais de ~30 arquivos visíveis), você pode distribuir a leitura e as explicações entre subagentes, uma seção ou bloco de arquivos por subagente. Passe para cada um estas regras de escrita (seção 5) e peça de volta só o objeto `explanations` do bloco. Cada subagente escreve em `<work>/explanations-N.json`, e você junta tudo em `decisions.json`.

**Cache:** se `cached.explanation` ou `cached.noise` existir, reutilize a decisão **sem reescrever**. A chave do cache é o caminho mais o hash do conteúdo antigo e do novo, então a entrada só existe se o arquivo for idêntico ao da rodada anterior. Só decida de novo se a decisão antiga contradisser o patch atual; nesse caso, avise o usuário.

## 3. Ruído por julgamento

Mande para `noise` um arquivo cujo patch inteiro se encaixa em um destes casos:

- troca mecânica de um elemento por outro equivalente, repetida em vários arquivos (por exemplo, `<img src="/x.svg">` por `<XIcon />`), quando o componente novo aparece em outro arquivo das seções;
- ajuste de tipo, fixture ou valor padrão que só acompanha uma mudança de contrato já explicada em outro arquivo (por exemplo, um campo novo adicionado ao objeto de teste ou ao default de uma config);
- asserções de teste atualizadas apenas para refletir uma configuração que mudou em outro arquivo;
- arquivo gerado por ferramenta (schemas, manifests gerados) que o smart-diff não conhecia;
- documentação cujo conteúdo novo é só link, reformatação ou uma nota que repete o que as seções já explicam;
- alias ou flag de configuração de build/teste sem efeito no comportamento do produto.

Nunca é ruído:

- mudança de condição, valor, limite, mensagem de erro, permissão, rota, variável de ambiente, dependência nova ou versão de runtime com efeito;
- arquivo com `symbols` exportados adicionados ou com assinatura alterada;
- qualquer arquivo que outro arquivo das seções precise para ser entendido.

Na dúvida, o arquivo fica nas seções. O `reason` diz em uma frase o que o arquivo faz e por que não precisa de atenção, citando o arquivo que explica a mudança real quando houver. Exemplo: `"Troca <img src=\"/brain.svg\"> por <BrainIcon>; sem lógica."`

## 4. Seções

- Cada seção é um fluxo que o leitor percorre de uma vez: contratos compartilhados, uma funcionalidade no backend, as rotas que a expõem, a tela que a consome, um script, uma mudança de configuração da build. Ponha a camada no título quando ajudar, por exemplo "Backend — triagem de cards".
- **A ordem final (seções concatenadas) deve manter todo arquivo depois dos arquivos alterados de que ele depende** (`dependsOn`). Comece pela `order` do smart-diff e só a altere para agrupar. Se um arquivo precisa de outro de uma seção posterior, mova a seção inteira ou o arquivo. O `assemble` recusa violações e diz qual par está errado.
- Testes vêm logo depois do arquivo que testam. Um teste que importa as rotas de produção vem depois do arquivo das rotas, não na seção da funcionalidade.
- Documentação que especifica uma funcionalidade pode abrir a seção dela.
- `summary`: uma ou duas frases dizendo o que o fluxo faz. Quando houver um caminho claro, descreva-o (`rota → service → client → policy`).
- Sem seções de um arquivo só, exceto quando o arquivo é de fato independente.

## 5. Explicações

Escreva em pt-BR, com linguagem simples e objetiva, para quem nunca viu o código. Descreva comportamento observável (entradas, saídas, limites, erros, estado), não a sintaxe.

| `kind` / `status` | Campos |
| --- | --- |
| `code` modificado | `before` e `after` (obrigatórios) |
| `code` novo | `after`; `before` é opcional e vira "Não existia." quando omitido. Use `before` para dizer como o sistema se virava sem o arquivo, se isso ajudar. |
| `test` | `tests`: o que o teste garante, em uma frase por grupo de casos |
| `doc` / `config` | `after`: o que o conteúdo muda ou especifica; `before` quando a configuração antiga importa |

Regras:

- Toda afirmação precisa sair do patch ou dos `symbols`. Se não der para saber pelo diff, não escreva. Não invente motivação nem histórico.
- `before` descreve só o comportamento que existia e mudou; `after`, o comportamento novo. Não repita no `after` o que continua igual.
- Cite números e regras concretas: limites (500 caracteres, 30 s), defaults, precedências (variável de ambiente antes do valor salvo), códigos HTTP, o que é cacheado e por quanto tempo, o que é validado e o que acontece em caso de erro.
- Use os nomes do código entre crases só quando o leitor precisar localizá-los (funções exportadas, rotas, campos de contrato). Prefira nomear pelo papel: "o formulário de novo card", não "`CardForm`".
- Para arquivos que só foram extraídos de outro, diga de onde vieram e o que mudou na extração: "Extraído de RepositoriesPage.tsx sem mudanças; novidade: …".
- Quando um detalhe do patch parecer um bug ou incoerência (uma rota registrada que sempre responde 405, por exemplo), registre o fato no `after` sem especular e mencione ao usuário no final.
- Tamanho: de uma a seis frases por campo. Se precisar de mais, o arquivo provavelmente tem mudanças independentes; descreva cada uma em uma frase.

Exemplo de arquivo modificado:

```json
"server/chat/service.ts": {
  "before": "A mensagem do usuário ia exatamente como digitada para o Claude/Codex.",
  "after": "Antes de enviar, a mensagem passa por repositoryMentionContext, então o agente recebe também a lista de repositórios mencionados com os caminhos."
}
```

## 6. Montar e validar

Formato de `<work>/decisions.json`:

```json
{
  "noise": [{ "path": "src/App.tsx", "reason": "…" }],
  "sections": [{ "title": "…", "summary": "…", "files": ["shared/domain/x.ts", "server/x.ts"] }],
  "explanations": { "shared/domain/x.ts": { "before": "…", "after": "…" } }
}
```

```bash
node "<script-de-revisao>" assemble <work>/report.json <work>/decisions.json <saída> --cache <cache>
```

`<saída>`: o caminho que o usuário pediu; senão `<work>/review.json`. O `assemble` confere que:

- todo arquivo visível está em exatamente uma seção ou em `noise`;
- nenhum arquivo aparece duas vezes;
- nenhuma dependência aparece depois de quem a usa;
- as seções têm título único, resumo e arquivos;
- todo arquivo das seções tem os campos de explicação exigidos pelo seu tipo.

Se houver erros, ele lista todos e não escreve nada. Corrija `decisions.json` e rode de novo até sair com código 0. Depois de um `assemble` bem-sucedido, o cache guarda as decisões para a próxima rodada.

Estrutura do JSON final (`schemaVersion: 2`):

- `comparison`: copiado do relatório;
- `source`: hashes do relatório e das decisões;
- `readingGuide` e `stats`;
- `sections[]`: cada arquivo tem `order`, `id`, `status`, `path`, `kind`, `dependsOn`, `usedBy`, `explanation`, `symbols`, `omittedHunks` (quando o smart-diff tirou trechos de formatação) e `patch` (filtrado);
- `noise[]`: cada item tem `source` (`smart-diff` ou `judgment`) e `reason`;
- `warnings`.

## 7. Responder ao usuário

Diga em poucas linhas:

- o caminho do JSON final e do `decisions.json`;
- quantos arquivos ficaram em seções e quantos são ruído, separando o que o smart-diff recolheu do que foi julgamento seu, com a lista dos arquivos de ruído por julgamento;
- quantas decisões vieram do cache;
- qualquer incoerência ou possível bug que você notou nos patches.

Não cole o JSON na resposta.
