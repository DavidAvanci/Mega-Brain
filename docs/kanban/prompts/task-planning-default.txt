## Instruções de planejamento

### 1. Entenda e investigue

Consulte links fornecidos somente para leitura. Confirme o id da tarefa e classifique-a como bug, feature, refactor ou chore/migração. O id deve constar nos dois artefatos. Identifique os repositórios reais envolvidos e pesquise os pontos relevantes no código. Baseie afirmações em evidências; cite caminhos como `repo/path:line`.

### 2. Escreva PLAN.md

Em português, em `<artifact dir>/PLAN.md`, registre apenas contexto necessário para revisar e executar a tarefa. A checklist é a única lista de trabalho: não repita nela as ações, arquivos ou dependências.

```markdown
# PLAN
issue: <slug ou chave do card>
title: <resumo>
type: <bug | feature | refactor | chore>
estimate: <ex.: 2h 30m>

## Repositórios afetados
- `<repo>` — <papel da mudança>

## Contexto e decisões
- `<repo/path:line>` — <constatação que influencia a solução>
- <decisão e motivo, somente quando não forem óbvios pelo código>
```

Regras:

- `Repositórios afetados` é a primeira seção. Liste só repositórios que realmente receberão alterações.
- Inclua em `Contexto e decisões` somente evidências, contratos, restrições ou decisões que o executor não consiga inferir da checklist e do código.
- Use snippets curtos de código, JSON ou tipos quando eliminarem ambiguidade. Evite blocos longos; prefira contratos literais pequenos a explicações extensas.
- Contexto específico de um executor deve ir no campo `context` do item em TASK-CHECKLIST.json. Não dependa de headings por ID no plano para transmitir instruções.
- Riscos só entram quando forem relevantes e não óbvios. Não crie seções vazias.
- Não inclua plano por repositório, resumo para PR, critérios de conclusão/Definition of Done, etapas de implementação ou uma segunda lista de tarefas.
- O resumo do PR será montado após a implementação, a partir das tasks concluídas da `TASK-CHECKLIST.json`.
- Seja conciso: não há meta mínima de palavras. Para uma tarefa comum, algumas linhas são suficientes; expanda apenas para explicar contratos ou decisões que afetem a implementação.

### 3. Escreva TASK-CHECKLIST.json

Em português, em `<artifact dir>/TASK-CHECKLIST.json`, grave JSON válido, sem fences. Ela contém somente ações atômicas de implementação. A checklist é a fonte única das tasks; cada item declara seu repositório e dependências explicitamente.

Não crie itens para testes, criação/alteração de arquivos de teste, validação, conferência, QA, smoke tests, revisão visual, screenshots ou verificação manual/automatizada. Não acrescente “e validar”, “e conferir” ou “e testar” às ações. Verificações são executadas pelo fluxo próprio.

Cada item recebe um id sequencial (`T1`, `T2` etc., global entre repositórios). O scheduler usa os campos estruturados para paralelizar itens em arquivos distintos e respeitar dependências:

```json
{
  "schemaVersion": 1,
  "issue": "<id do card>",
  "items": [
    {
      "id": "T1",
      "title": "<ação atômica>",
      "repo": "<alias cadastrado>",
      "files": ["src/database/migrations/*"],
      "requires": [],
      "creates": [],
      "deps": [],
      "context": "<contratos e decisões específicos deste item>",
      "completionCriteria": ["<comportamento entregue pelo item>"],
      "state": "pending"
    }
  ]
}
```

Metadados e dependências:

- `files`, `requires`, `creates` e `deps` são arrays de strings. `files` lista todos os caminhos/globs alterados, inclusive arquivos compartilhados. Sobreposição no mesmo repo serializa itens; `files: []` serializa em relação ao repo inteiro.
- Para remoção/renomeação de símbolo exportado, refatoração ampla ou codemod, use `files: []` salvo se todos os consumidores estiverem mapeados.
- `requires` declara pré-condições; `creates` declara arquivos produzidos pelo item. Migrações/bases obrigatórias vão em `card.json` (`requiredBases`) e também nas dependências. `timeoutMinutes` e `maxAttempts` são inteiros positivos opcionais.
- `deps` contém somente IDs reais, sem ciclos, ou `[]`. Um consumidor depende do item que produz seu contrato, inclusive entre repositórios, salvo se o contrato literal estiver no `context` do item.
- `context` e `completionCriteria` tornam cada item autocontido. Os critérios descrevem a entrega, sem criar tarefas separadas de testes ou verificação.
- Estados: `pending`, `done`, `failed`, `blocked` e `discarded`. Novos itens começam em `pending`. Para descartar um item, preserve seu ID com `state: "discarded"` e `discardReason`; o scheduler e o total executável o ignoram. Atualize deps dos consumidores para os novos IDs.
- `notes` é um array de strings reservado ao scheduler. Não inclua campos desconhecidos, comentários JSON, metadados inline ou checkboxes Markdown.
- Inclua observabilidade, validação de entrada ou tratamento de erro quando forem comportamento do produto. Não crie tasks apenas para comprovar a implementação.

### 4. Estime e reporte

Registre `estimate:` com base no escopo e nos riscos. Não crie branches, worktrees ou symlinks durante o planejamento; o scheduler prepara as worktrees na execução.

Ao concluir, reporte id e tipo da tarefa, caminhos dos artefatos, repositórios afetados e estimativa.
